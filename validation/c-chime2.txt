fix(desktop): the approval chime was never reaching the shell, and could not say so

User test on 0.9.15: no sound, either Alt-Tabbed away or with the window focused.

Root cause: this UI is NOT the bundled splash. boot_core navigates the window to
the loopback core, so assets.ts runs on a REMOTE origin. The chime called
window.__TAURI__.core.invoke(...).catch(() => {}) — and a rejected invoke was
discarded, then it fell through to the web-audio path that is already known to
be blocked by the autoplay gate. Denied IPC and blocked audio produced exactly
the same observable result: silence.

Two changes, both about being unable to tell what happened:

1. playChime now reaches for window.__TAURI_INTERNALS__.invoke first — that is
   the entry point Tauri actually injects on a remote origin — and falls back to
   the global only if it is absent. Failures are logged with a [chime] prefix
   instead of swallowed.

2. approval_chime now returns Err when PlaySoundW refuses, instead of always
   returning Ok(()). Previously the command "succeeded" whether or not a sound
   came out, so neither side of the IPC could tell a working call from a dead one.

Smoke gains a guard so this cannot regress into silence: the chime must reach
for the loopback-origin entry point and must NOT contain a bare catch that
discards the result. The old "plays on a permission prompt" check is kept
separately, because "the native route is reachable" and "the native route is
actually called" are different failures.

Gates: tsc 0 | smoke PASSED (all four chime checks).
