fix(security): prototype-pollutable and type-confused cue preferences

Found in an audit sweep of the cue settings added in 3be9d10.

loadCues did Object.assign({}, CUE_DEFAULTS, JSON.parse(raw)). Two defects:

1. PROTOTYPE POLLUTION. JSON.parse produces a __proto__ key as an OWN property,
   and Object.assign copies it via [[Set]], which walks the __proto__ setter and
   REPLACES the object's prototype. Verified: with a stored object carrying a
   __proto__ entry, out.tone resolved to the inherited value. Confined to this
   one object - not global Object.prototype - but still wrong.

2. TYPE CONFUSION. A stored "false" (string) is TRUTHY, so a user who had
   switched a cue off would still hear it. There was no type validation at all.

Fix: copy key by key from an explicit CUE_KEYS allowlist, each guarded by a
typeof check against the default. Verified against 8 inputs - proto pollution,
unknown keys, wrong types, malformed JSON and null all fall back to defaults,
while the global-tone migration and a valid per-cue split still work.

Also swept: no other Object.assign in src/ has this shape (the rest use literal
keys or a clean base). ACL chain re-audited - all 6 commands have a build.rs
manifest entry AND a loopback capability grant, with no orphaned permissions.
