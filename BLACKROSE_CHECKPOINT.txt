THE S0/S1 BUG (rooted 2026-10-04, after two failed attempts)
  The data on disk was always correct. S0/S1 were renderRich's OWN stash
  sentinels: keep() wraps each generated tag in NUL+"S"+index+NUL so later
  regexes cannot match inside markup it just produced, and the result is
  assigned to innerHTML. The HTML parser is REQUIRED to rewrite U+0000 in the
  input stream to U+FFFD, so any sentinel reaching innerHTML came back as
  visible garbage, replacing the value ("2.01%") with "S1".
  Sentinels are now Private Use Area chars (U+E000/U+E001), which pass through
  untouched, plus a final sweep that removes any NUL/FFFD-wrapped S<digits>.

- U+FFFD AROUND S0/S1 - ROOT CAUSED AND FIXED (2026-10-05)
    It was never a display bug. The raw bytes named it: the stored chunk was
    UTF-16LE read as UTF-8, i.e. NUL-interleaved text with the BOM destroyed
    into two U+FFFD. Windows PowerShell 5.1 writes UTF-16LE by default, and
    Node's utf8 decoder is lossy BY DESIGN (a lone high byte becomes U+FFFD
    with no error thrown), so learn_file accepted the file, chunked the
    corruption, and PERSISTED it. That is why it never reproduced: the source
    file is gone but the damaged copy survived in the knowledge base.

    Evidence (knowledge/c-users-pc-desktop-blackrose-cline-blackrose-router-chain-txt.json,
    saved 2026-09-20). Bytes around the damage:
      20 22 EF BF BD EF BF BD 42 5C 75 30 30 30 30 6C 5C 75 ...
         \__U+FFFD__/        B \ u0000      l \ u0000
    296 interleaved NULs in a single chunk; only the 2-char BOM was lost.

    TWO bugs, not one:
      1. Silent corruption - learn_file and learn_folder read every file as
         UTF-8. Fixed with decodeTextFile(): sniffs a BOM, else tests for the
         strict all-odd-bytes-zero UTF-16LE pattern, and decodes properly. A
         UTF-8 BOM is now stripped so it cannot leak into the first chunk.
      2. Silent data loss - learn_folder sniffed for binary BEFORE decoding, and
         UTF-16 files are full of NULs, so every PowerShell-written file was
         SKIPPED AND NEVER INGESTED. Arguably worse than the garbling.

    The sniff is deliberately strict (all odd bytes zero AND all even bytes
    printable). A density threshold was tried first and smoke caught it: the
    existing binary fixture [0x41,0x00,0x42,0x43,0x00] is 40% NUL by chance
    and got misclassified as text. Pinned as a regression test.

    Repaired the one damaged chunk in the live data dir (594 chars -> 296
    clean, zero NULs, zero U+FFFD). source/kind/saved preserved. Backups at
    <file>.bak-20261005 and %TEMP%\chain-original.json. Full-dir rescan:
    zero U+FFFD remaining. scripts/repair-knowledge-chunk.ts is the guarded,
    idempotent repair tool.
